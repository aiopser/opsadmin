# 定时任务调度与执行历史

定时任务与手动发起流程都生成 WorkflowRun，均在「任务系统 → 执行历史」查看。
执行类型描述执行内容（流程执行）；触发方式描述入口（定时触发、手动触发、API 触发）。
定时任务页的「立即执行」记录为手动触发，保留来源定时任务的编号与名称快照。
可从定时任务的「执行历史」按钮按来源过滤，也可在历史页面按触发方式筛选。

## 调度规则

- 使用 `apps.jobs.scheduler:ScheduledJobScheduler`，继承 django-celery-beat DatabaseScheduler。
- 每个任务独立采用其配置的时区；应用仍支持 `USE_TZ=False`，Beat 的 naive 游标按 UTC 解释。
- Cron 五个字段必须同时满足，与 Celery 原生语义一致；日和周同时限定时采用 AND。
- Beat 在消息发出前固定 `scheduled_for`；数据库游标推进不改变该消息的发生时刻。
- Worker 用任务编号、发生时刻唯一结果行去重；过期策略依据原始时刻计算。
- 修改 Cron、时区或启用状态会更换消息令牌，旧定义的积压消息被拒绝。
- 仅修改名称、参数等配置以及重复执行同步命令，不重置 Beat 已有游标。
- 重叠排队合并为一次补跑，后续周期逐项记录合并结果；补跑被拒后记录原因，结束本次补跑。

## 更新运行环境

1. 同时更新 API、Worker、Beat 代码，并停止旧版 Beat。
2. 在 `backend/` 执行 `python manage.py sync_scheduled_jobs`，同步消息令牌和调度定义。
3. 重启 Worker 和 Beat，确保 Beat 使用配置中的 `apps.jobs.scheduler:ScheduledJobScheduler`。
   启动命令若显式指定原生 `--scheduler`，须同步修改或移除该覆盖参数。
4. 旧格式消息缺少发生时刻或令牌时会被拒绝，不会自动转换后执行。

本次无需新增数据库迁移。历史运行不回填、不重写；历史记录未保存来源名称时保持空值。
未生成运行的跳过、合并、过期等结果保留在定时任务最近调度结果中，不伪造执行历史。
