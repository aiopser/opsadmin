# Playbook 与 Module 执行资源检查及优化建议

检查日期：2026-10-26。范围为资源列表、新增编辑、版本管理、参数转换、快速执行及后端发布和执行衔接。本轮未修改业务代码。

## 结论

保留公共的资源与版本管理框架，将内容编辑区按 Playbook、Module 的实际语义拆分。先解决参数保存和版本一致性，再统一布局。不要继续要求普通用户维护一套与 Ansible 重复的参数模式。

## 一、已经复现的问题

| 优先级 | 问题及触发条件 | 影响 | 建议 |
| --- | --- | --- | --- |
| P1 | 已有 Module 默认参数存于 `default_vars.module_args`，但没有对应 schema；解析得到空参数行，再保存会重建或删除 module_args | 默认参数静默丢失 | 从实际参数反向构造编辑模型；保留未展示字段；保存失败时保持表单。增加无 schema、部分 schema 和字符串参数的往返测试 |
| P1 | 参数默认值转换将 `yes` 转为 false；integer 接受 1.5；同名参数最后一项覆盖前一项 | 页面配置与实际执行值不一致 | 使用与类型匹配的输入控件；非法值阻止保存；参数名称查重。若简化为原生参数编辑，也须校验输入并避免隐式转换 |
| P1 | 版本保存的两次点击同时等待表单校验，校验完成后分别提交 | 产生重复请求 | 提交入口立即加锁，finally 解锁；后端保证创建版本的并发一致性 |
| P1 | 在资源 A 发布请求返回前切换到 B，回调直接修改 currentCommand | B 的界面状态被 A 的结果污染 | 捕获资源 ID 和操作代次；仅更新匹配上下文。保存、归档、复制均使用相同规则 |
| P1 | 两个发布请求在归档旧版本与发布新版本之间交错 | 两个版本同时处于 published | 在事务中锁定同一资源，串行完成旧版本归档与新版本发布；增加并发发布测试及数据库约束评估 |

复现方式：直接运行现有 TypeScript helper，并抽取实际 Vue 提交函数进行内存异步测试；后端使用隔离 SQLite 测试数据库、实际 serializer 与发布视图构造交错顺序。没有访问真实主机或云 API。

关键复现结果：无 schema 的既有默认参数编辑后为空；`yes → false`；`1.5 → 1.5`；重名 state 保留最后一个值；双击保存发起两次请求；发布交错的两个响应均为 200，最终 publishedVersions 为 `[3, 2]`。

## 二、从代码确认的能力与体验缺口

1. **Module 套用了文件资源的导入方式。** 当前同样提供 YAML 文件上传和 Git 单文件读取，但 Module 实际需要的是模块名与参数。建议移除不适用的来源选项；“模块短名”改为“Ansible 模块名”，优先展示 FQCN，例如 `ansible.builtin.service`。
2. **超时存在于模型和请求，但没有编辑控件。** 默认 60 秒，用户在版本表单中无法调整。应在高级配置中展示“执行超时”，明确单位及其在流程中的覆盖关系。
3. **内容修改入口过深。** 列表“编辑”只改基础信息，执行内容要经过“更多 → 版本管理 → 编辑草稿”。建议明确使用“编辑信息”“编排/编辑内容”“版本管理”，并让编辑内容直接进入已有草稿，或基于已发布版本创建草稿。
4. **单一执行类型仍占据一行。** Playbook、Module 各只有一个可选类型，直接由资源分类确定，不必展示只有一个选项的单选控件。
5. **创建资源与首版本分成两个请求。** 首版本失败时，资源已经存在，表单仍然关闭。建议原子创建，或保留编辑上下文并明确继续补充首版本，避免重复创建。
6. **切换模块不清理不相容参数。** 有参数行时切换模块名不会重新匹配；“加载内置参数”则直接覆盖。应显示替换影响，保留兼容参数，丢弃内容前确认。
7. **参数帮助不是模块真实 schema。** 内置字典按短名匹配，可能把其他 collection 的同名模块当作 builtin；类型初始化为 string。应标明为参考帮助，按完整模块名区分。后续可从实际执行环境的 ansible-doc 获取元数据，但不能让静态帮助冒充运行时校验。
8. **资源选择只加载前 100 条。** 快速执行和克隆选择等入口可能选不到后续资源。应采用后端搜索与分页，编辑已有引用时单独回显选中项。
9. **Playbook 快速选择存在过期响应风险。** 切换资源后旧请求仍可回写版本和内容。应采用请求代次，并在切换来源、重置和卸载时使旧请求失效。
10. **版本操作体验不完整。** 新建版本默认空白；归档版本没有复制入口；详情缺少充分版本上下文；备注未在列表体现。建议提供“基于此版本创建草稿”、版本说明与内容对比。
11. **关闭编辑缺少未保存提示。** 抽屉关闭应检测脏数据；保存错误保持内容，避免重新录入。

### 执行契约需一起明确

- Playbook serializer 当前验证 YAML 非空列表及字典结构，不等于 Ansible 语法或可执行性验证。隔离测试中 `- not_an_ansible_play_keyword: hello` 可以通过 serializer。建议分开显示“YAML 格式校验”和执行环境中的 Ansible 校验结果。
- Git 当前只导入单文件，执行器写入临时 project 下的 playbook.yml，没有完整导入同仓库的 roles、files、templates。页面应明确“导入单文件”；完整项目支持作为独立后续能力。Ansible Runner 本身支持 project 目录及其 roles，限制来自本项目的导入和组装方式。[Runner 官方说明](https://docs.ansible.com/projects/runner/en/stable/intro/)
- Playbook 的 hosts 会改写为 all，但 delegate_to 保留。隔离构建测试确认 `hosts: web` 变为 all，而 `delegate_to: localhost` 仍在。应明确原始分组语义、步骤目标和控制端执行策略，并在执行前预览中说明委托执行；不能仅凭 hosts 归一化就声称所有执行都限制在选中主机内。[Ansible 委托执行说明](https://docs.ansible.com/projects/ansible/latest/user_guide/playbooks_delegation.html)
- “检查模式不真正修改主机”表述过于绝对，应说明取决于模块支持和任务配置，`check_mode: false` 可使任务正常执行。[Ansible 检查模式说明](https://docs.ansible.com/projects/ansible-core/devel/playbook_guide/playbooks_checkmode.html)
- `free-form` 是帮助文档中的参数表达方式，不宜当作普通 JSON 参数名。应分别校对 command、shell、raw、script 的原生参数语义，并验证页面、预览与 Runner 构造结果一致。

## 三、推荐页面结构

### 公共列表

沿用项目已有搜索卡片、列表工具栏、Element Plus 表格和抽屉，不增加新 UI 库。列表保留名称、编码、可用状态、已发布版本、草稿、更新时间和操作；Module 按需增加模块名。状态名称区分资源可用性与版本发布状态，避免两个层次都叫“已发布”。

名称作为主要阅读入口；版本、状态、数字和操作对齐一致；长名称可省略但能查看完整内容。标准按钮尺寸、普通主题文字、适量辅助文字，不用大面积强调色和重复标题。

### Playbook 编辑

```text
基础信息：名称 / 编码 / 描述 / 风险等级

内容来源：手动编写 ○  上传文件 ○  Git 单文件 ○
Playbook 内容
┌──────────────────────────────────────────┐
│ YAML 编辑器，提供格式校验、定位错误          │
│ 以内容为主，编辑区可扩展                    │
└──────────────────────────────────────────┘
额外变量 extra_vars
┌──────────────────────────────────────────┐
│ 统一项目约定的原生变量编辑方式              │
└──────────────────────────────────────────┘
高级配置 ▸ 执行超时 / 提权 / 检查模式支持

                               取消  保存草稿
```

不再让新资源额外维护参数模式和输出提取器；旧数据保留兼容入口。变量格式须沿用后端现有契约，若新增 YAML 输入，应先统一解析及校验规则。

### Module 编辑

```text
基础信息：名称 / 编码 / 描述 / 风险等级

Ansible 模块名  [ansible.builtin.service          ]
模块说明与参数参考 ▸

默认模块参数
{ "name": "{{ service_name }}", "state": "restarted" }

额外变量 extra_vars
{ "service_name": "nginx" }

高级配置 ▸ 执行超时 / 提权 / 检查模式支持
                               取消  保存草稿
```

模块参数回答“调用模块时传什么”，extra_vars 回答“模板变量取什么值”，两者不合并为同一个含义。可提供简单键值编辑与 JSON 编辑切换，但必须无损往返；布尔值、数字、列表与对象不能全部用文本隐式转换。shell/command 等自由命令场景应有适配原生语义的命令输入。

### 版本管理

- 固定显示“资源名 · 版本管理”，资源可用状态与版本状态分区清晰。
- 主按钮优先“编辑草稿”；无草稿时“基于已发布版本创建草稿”，另提供空白草稿。
- 版本列表展示版本、状态、版本说明、时间和紧凑操作；归档版本也能作为新草稿来源。
- 版本详情明确资源名、版本号和只读状态；Module 名用单行展示，不用 460px 高的代码编辑器。
- 编辑内容与版本列表尽量保持稳定上下文，减少多个抽屉关闭再自动打开的跳转。
- 表单遵循项目已有字体、间距与主题变量。参数表不继续堆叠六列表头和大量 12px 小字。

## 四、建议实施顺序与验收

1. **正确性：** 默认参数无损保存、类型及重名校验、防重提交、异步上下文隔离、版本发布事务及并发版本号分配。
2. **编辑体验：** 拆分 Playbook 与 Module 内容区，补超时，精简重复类型与不适用来源，明确模块参数与 extra_vars。
3. **版本与视觉：** 直接进入草稿、复制历史版本、稳定抽屉上下文、未保存保护、统一字体及操作尺寸。
4. **执行能力：** Ansible 环境校验、完整 Git 项目、实际环境模块帮助。根据真实需求逐项增加，不让当前表单继续承担未实现能力。

验收至少覆盖：旧 Module 默认值编辑无变化；布尔/数组/对象往返；重复参数拒绝；双击只提交一次；切换资源后旧响应不污染；并发发布只保留一个已发布版本；超过 100 个资源仍可搜索选择；首版本失败可继续编辑；模块实际参数与预览一致；Playbook 委托执行和项目依赖有明确处理规则。
